# RAG-инструмент `rag_tool`

RAG по справочнику для бота разметки TagMe. Для каждой записи находит в справочнике `top_n` наиболее близких
по смыслу текстов, добавляет их на вход как поле `reference` и вызывает LLM обычными средствами бота.

Состав папки:

| Файл | Назначение |
|------|------------|
| `build_reference.py` | Готовит справочник: считает эмбеддинги и создаёт JSON для загрузки в TagMe |
| `rag_tool.py` | Сам инструмент: загрузка справочника, поиск, вызов LLM |
| `recall_check.py` | Считает recall поиска по выгрузке результатов разметки (GOLDEN и `final_user_prompt`) |

## Как это работает

1. Справочник загружается из датасетов TagMe.
2. Входные данные (INPUT: ...) должны содержать поле, начинающееся с search_ (например, `search_dialog`).
   Эмбеддинг его значения считается как есть, без инструкции и префикса.
3. По косинусной близости выбираются `top_n` записей справочника. Список их описаний (поле `description`)
   в порядке убывания релевантности записывается в поле `reference`.
4. Входные данные вместе с `reference` отправляются в LLM.
5. К ответу LLM добавляется поле `emb_tokens` (токены на эмбеддинг запроса).

## Входные данные задачи

Входные данные должны содеражать ровно одну колонку `INPUT:` с `search`. Это необходимо, если не все входные данные для LLM должны участвовать в семантическом поиске. Эмбеддинги будут считаться именно для этой колонки. Пример:
- INPUT:full_context
- INPUT:search_user_problem

Ошибка возникает, если:
- `input_data` не dict (например, строка);
- полей `search_*` нет или их несколько;
- значение поля `search_*` пустое или не строка.

## Подготовка справочника

### Входной файл (csv или xlsx)

Обязательные колонки:

| Колонка | Что содержит |
|---------|--------------|
| `description` | Текст, который попадёт в `reference` и будет показан LLM |
| `emb` | Текст, для которого считается эмбеддинг (по нему считается косинусная близость) |

Требования:
- Обе колонки заполнены в каждой строке. Пустые значения вызывают ошибку с номерами строк файла.
- Если эмбеддер требует инструкцию или префикс для документов, их нужно добавить в колонку `emb` самостоятельно.
- Значения читаются как строки (`dtype=str`). Лишние колонки игнорируются.

### Запуск

Из директории `tagme_bot/`:

```bash
python build_reference.py PATH [--service direct] [--model MODEL]
```

| Аргумент | По умолчанию | Описание |
|----------|--------------|----------|
| `PATH` | обязательный | Путь к csv или xlsx со справочником |
| `--service` | `direct` | Стенд эмбеддинга: `direct`, `ift`, `vsellm` |
| `--model` | `Giga-Embeddings-instruct-10B-A1.8B-0826` | Модель эмбеддера |

Что делает скрипт:
- Считает эмбеддинг колонки `emb` для каждой строки (до 3 попыток на строку) и проверяет единую размерность.
- Каждые 10 записей печатает прогресс, в конце печатает суммарное число токенов и путь к результату.
- Создаёт файл `<имя входного файла>.json` **в директории входного файла**.
- Завершается с кодом 0, только если посчитаны все эмбеддинги. Иначе печатает `ОШИБКА: ...` и завершается с кодом 1.

При `--service direct` прокси не возвращает `usage`, поэтому суммарное число токенов будет 0.

### Формат результата

JSON-массив, ключ с названием модели эмбеддера содержит вектор:

```json
[
  {"description": "Текст записи", "Giga-Embeddings-instruct-10B-A1.8B-0826": [0.012, -0.034, ...]},
  ...
]
```

Файл может содержать другой ключ-модель. Инструмент берёт тот, что указан в `emb_model`.
Размерность вектора запроса должна совпадать с размерностью справочника.

### Куда загрузить

Полученный JSON загружается вручную в раздел **датасетов** TagMe:

| Домен | Организация |
|-------|-------------|
| cloud (`tagme.sberdevices.ru`) | «Центр корпоративных решений» |
| sigma (`tagme.sigma.sbrf.ru`) | «Razmetka.team» |

Инструмент по стенду сам выбирает организацию: cloud `2bdf1e09-59e1-469c-b055-f81891aa3e64`,
sigma `2673e31b-8602-48c9-bf5f-8be78bfc6f47`. **На стенде `sberdev` инструмент не работает.**

После загрузки скопируйте id файла (или ссылку на него) для параметра `reference` в конфиге бота.

## Конфиг бота

В конфиге бота (для cloud):

```json
{
  "model": "rag_tool",
  "reference": "https://tagme.sberdevices.ru/files/35714fde-8007-4747-8432-92866a2b9e09",
  "emb_model": "openai/text-embedding-3-small",
  "emb_service": "vsellm",
  "top_n": 20,
  "llm_model": "<модель LLM>",
  "service": "<сервис LLM>",
  "temperature": 0,
  "max_new_tokens": 2048,
  "seed": 567
}
```

| Параметр | Обязателен | По умолчанию | Описание |
|----------|:----------:|--------------|----------|
| `model` | да | | Всегда `rag_tool` |
| `reference` | да | | Id файла справочника или ссылка `https://.../files/<id>`; id берётся после `files/` |
| `llm_model` | да | | Модель LLM |
| `emb_model` | нет | `openai/text-embedding-3-small` | Модель эмбеддера. Должна совпадать с ключом в справочнике |
| `emb_service` | нет | `vsellm` | Сервис эмбеддера: `direct`, `ift`, `vsellm` |
| `top_n` | нет | `10` | Сколько записей справочника брать. Если больше размера справочника, берётся весь справочник |
| `service` | по политике стенда | | Сервис для LLM (как в обычной LLM-ветке) |
| `temperature`, `max_new_tokens`, ... | нет | | Параметры генерации, как в обычной LLM-ветке |
| `think`, `web_search`, `url_context`, `reasoning_effort` | нет | | Работают так же, как в обычной LLM-ветке |

Особенности:
- `service` относится только к LLM, `emb_service` только к эмбеддеру.
- Политика стенда применяется к обоим. Например, на sigma `vsellm` запрещён и для LLM, и для эмбеддера.
- Параметр `user_prompt` инструментом не используется. Медиа (изображение, видео, аудио) и chain не поддерживаются.

## Токены

- Токены вызова LLM, reasoning и think учитываются в статистике бота так же, как в обычной LLM-ветке.
- `emb_tokens` добавляется в ответ отдельным полем. При `emb_service=direct` он равен 0, так как прокси
  не возвращает `usage`. Для `vsellm` значение реальное.

## Обработка исключений

Любая ошибка (нет поля `search_*`, нет ключа `emb_model` в справочнике, ошибка загрузки, сбой эмбеддера или LLM,
несовпадение размерности, ответ не JSON) пробрасывается как есть. Бот обрабатывает её по обычным правилам:
`own_model_failed: <тип>: <сообщение>`, повтор записи и `TECH_ERROR` через `TECH_AFTER_SEC`.

## Оценка recall поиска

`recall_check.py` проверяет, попал ли эталонный ответ в `reference`. Берёт выгрузку результатов проекта
(csv или xlsx), для каждой строки сравнивает значение колонки `GOLDEN:<--gold-col>` с полем `--ref-field`
записей `reference` из `OUTPUT:final_user_prompt`. Имена могут различаться: например, эталон в `GOLDEN:theme`, а в справочнике поле называется `topic`.

```bash
python recall_check.py PATH --ref-field FIELD --gold-col COL [--prompt-col COL] [--out-col COL]
```

| Аргумент | По умолчанию | Описание |
|----------|--------------|----------|
| `PATH` | обязательный | Путь к csv или xlsx с результатами |
| `--ref-field` | обязательный | Поле записи `reference`, с которым сравнивается эталон |
| `--gold-col` | обязательный | Имя колонки эталона без префикса `GOLDEN:` |
| `--prompt-col` | `OUTPUT:final_user_prompt` | Колонка с финальным промптом (JSON с `reference`) |
| `--out-col` | `OUTPUT:<--gold-col>` | Колонка с ответом бота. Если её нет, accuracy не считается |

Вывод: таблица с recall для k = 1, 3, 5, 10, 20, 30, … (шаг 10) в пределах `top_n`, последняя строка всегда
`recall@<top_n> (top_n)` (например, при `top_n=8`: 1, 3, 5, 8).
Далее accuracy бота (общая и отдельно для случаев, когда эталон есть и нет в `reference`), ранги
эталона по возрастанию. Строки с пустым GOLDEN или некорректным
`final_user_prompt` пропускаются, их число печатается строкой `пропущено строк: N` (только если такие есть). При ошибке печатается `ОШИБКА: ...`, код возврата 1.

Требование: записи `reference` в `final_user_prompt` должны содержать поле `--ref-field`.
